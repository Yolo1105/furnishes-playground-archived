助手
Yes—I understand what you’re discussing. **You want Furnishes to feel like entering and shaping a space, while letting someone move naturally from the whole room into one furniture piece and, when needed, its precise construction.** A casual user should still be able to make a simple choice without learning a design application.

I read your pasted conversation, the rendering/modeling plan, and the relevant product and experience documents, and checked the corresponding UI code. This is a grounded understanding of the direction, not a claim that I have audited every file.

**Can you call this an AI-agent project?**

Yes, broadly. My preferred description is **“an AI-assisted interior and furniture design platform with agentic workflows.”**

Your AI already does more than answer questions: it works with scene context, plans layouts, coordinates generation, and supports design evaluation. However, much of that follows predefined application workflows. A more autonomous agent would choose tools, inspect their results, and decide what to do next toward a user’s goal. That distinction is also how [Anthropic describes workflows versus agents](https://www.anthropic.com/engineering/building-effective-agents).

For Furnishes, a useful next agent capability would be:

> “Keep my existing desk, improve storage, and preserve access to the window.”

Eva would inspect the project, propose supported changes, check dimensions and compatibility, show a preview, and let the user apply or undo the result. That is a more valuable direction than adding more chat modes.

**Your full-screen idea is worth keeping—but floating controls need a clear hierarchy.**

The room can remain the main visual surface. The difficulty comes when users must simultaneously understand room navigation, furniture configuration, chat modes, tool windows, and planning.

Your current code exposes several of those concepts separately. For example, the [chat picker](/Users/mohanlu/Documents/furnishes-playground-standalone/src/components/chat/ModeDropdown.tsx) asks users to choose both an intent and an interaction style, while tools and the planner have separate surfaces. That is a plausible source of confusion; it still needs observation with actual users.

I would organize the experience around **one project with progressively deeper workspaces**:

1. **Explore: see something you like.**  
   Keep the large room or furniture view. Show a small set of clear actions: browse furniture, select an object, ask Eva, and save. Let users enter from a furniture item directly; creating a room or starting a conversation should be optional.

2. **Configure: change the selected piece.**  
   Clicking furniture opens one predictable inspector with its name, supported sizes, finishes, accessories, and configuration summary. The room remains visible. “Focus on this piece” isolates it temporarily; “Back to room” restores the previous camera and selection.

3. **Plan: arrange the space.**  
   Provide an explicit 2D/3D switch, placement tools, dimensions, and relevant clearance feedback. A lightweight user can stay here and work with familiar controls without opening construction tools.

4. **Detail: work precisely.**  
   “Edit construction” opens a dedicated workspace for orthographic views, panels, snapping, dimensions, and eventually feature history. This is where stable toolbars and docked panels make sense. It should edit the same object in the same project.

These are accessible workspaces, not a mandatory sequence or a “beginner versus professional” choice at onboarding. Showing advanced controls when they become relevant follows the established [progressive-disclosure principle](https://www.nngroup.com/articles/progressive-disclosure/).

On desktop, I would start with a compact navigation bar, contextual selection controls, and one main inspector. On mobile, use a bottom sheet with explicit viewing and editing states rather than shrinking several floating windows.

**The most important requirement is continuity.**

Imagine this journey:

> Browse a shelf → place it beside an existing desk → change its finish → inspect its dimensions → adjust a supported configuration → return to the room → compare two saved versions.

The shelf’s identity, configuration, placement, and history should survive every transition. Eva should understand the currently selected shelf automatically.

Your latest furniture-page document already calls for this continuity, optional chat, and saved configurations that restore more than a screenshot. It also describes a furniture page within the existing website; that narrower scope should not silently become a requirement to build the entire CAD platform immediately. :codex-file-citation{path="/private/tmp/furnishes-review/13.pdf" purpose="source"}

**The improvement plan has three connected parts, with different priorities.**

Your implementation document proposes two technical tracks: better rendering—materials, lighting, shadows, performance, and photo output—and deeper modeling—shared document data, floor plans, cabinets, panels, and later free-form CAD. Those support your vision, but they do not by themselves solve navigation and usability.

My recommended order is:

1. **Prove one complete user journey.** Browse, configure, place, inspect, save, and restore one representative furniture piece. Test whether users can complete it without coaching.
2. **Unify project state and editing.** Give objects stable identities and share configuration, selection, undo/redo, and saved versions across views. Keep temporary previews separate from accepted changes.
3. **Improve everyday visual quality.** Prioritize materials, lighting, believable scale, shadows, and responsive interaction. Treat the rendering plan’s exact dependencies and estimates as proposals requiring validation.
4. **Give Eva reliable editing tools.** Use structured actions with validation and visible previews, connected to the same editing system as manual controls.
5. **Expand precision and output where needed.** Add cabinet/panel workflows before committing to full free-form CAD; add photo rendering without making everyday use depend on it.

One essential distinction from your product documents: **an attractive AI-generated mesh is not automatically a configurable, manufacturable Furnishes product.** Concept exploration and validated product configurations can coexist, but purchase details and compatibility must come from actual product records. :codex-file-citation{path="/private/tmp/furnishes-review/03.pdf" purpose="source"}

My first concrete change would be the **room → selected furniture → configuration → detail → return** interaction. Making that transition clear would address your latest concern more directly than adding features or upgrading the renderer alone.

助手
**Yes—we can build “upload a room photo → get an editable 3D approximation of that room and its furniture.” Your current system only supports part of this.** A useful prototype could be relatively inexpensive; an accurate replica from one photo is a much harder promise.

**What your system currently does**

I checked the code:

- **Room photo:** it uses the image to guide style, colours, materials, and mood, then generates new furniture images and 3D models. It does not extract and reconstruct each original piece. See the [room pipeline](/Users/mohanlu/Documents/furnishes-playground-standalone/src/lib/pipeline/orchestrator.ts:455).
- **Single furniture photo:** it can send the uploaded image directly to an image-to-3D provider. This generates an approximation, with no guarantee of exact dimensions or hidden geometry.

So uploading your living room today might produce a room *inspired by it*, rather than reliably recreating your existing room.

**What we could add**

There are existing models we can integrate without training our own. For example, Meta’s **SAM 3D Objects** reconstructs objects from a photograph. Its fal API supports separate object meshes and placement metadata—useful for making the sofa, table, and chair individually selectable in Furnishes. [Meta’s implementation](https://github.com/facebookresearch/sam-3d-objects), [fal API documentation](https://fal.ai/models/fal-ai/sam-3/3d-objects/api).

The proposed flow would be:

1. Upload the photo.
2. Identify visible furniture and let the user correct the selection.
3. Reconstruct those pieces as separate objects.
4. Build an approximate floor-and-wall shell, with user correction.
5. Ask for a known measurement to establish scale.
6. Open the room in your existing full-screen editor.

**One photo cannot establish everything.** Hidden walls, the back of a sofa, and obscured objects must be inferred. A known measurement helps with scale but does not make every dimension accurate. More photos or a guided scan would improve the evidence.

**Is it cheap enough?**

There are two separate costs:

- **Generation cost:** potentially affordable. fal currently lists SAM 3D at **$0.02 per billing unit**, although we should verify how a multi-object request is metered before estimating a whole room. As another reference, Hunyuan Rapid costs **$0.375 per object with PBR materials**—eight objects would cost **$3 in mesh generation alone**, before analysis, preprocessing, retries, storage, and hosting. [SAM 3D pricing](https://fal.ai/models/fal-ai/sam-3/3d-objects), [Hunyuan Rapid pricing](https://fal.ai/models/fal-ai/hunyuan-3d/v3.1/rapid/image-to-3d).
- **Development cost:** my rough planning estimate is **1–2 developer-weeks for a narrow prototype**, reusing your viewer and upload infrastructure. A usable beta with object correction, scale adjustment, background jobs, recovery, and save/restore could take **4–8 developer-weeks**. These are estimates, contingent on testing reconstruction quality on real room photos.

An automatic, measurement-accurate room replica is outside that estimate.

**For your UX, I would introduce this as “Start from my room.”**

After uploading, users see an approximate reconstruction and can immediately choose **Keep**, **Move**, or **Replace** on existing furniture. Traditional and modular furniture can then be added through the same experience. Reconstructing an existing modular item would initially capture its appearance; understanding its component structure remains the later discussion.

That gives lightweight users a useful starting point without making them draw a floor plan or learn CAD. I’d validate it first on 10–20 varied room photos before committing to a larger build.

“我要这个柜子的这个尺寸、这套组成、这些颜色和配件，共一件。”

对模块化家具，用户可以从模板开始，也可以从 AI 推荐开始，但最后确认的必须是**你们实际能够提供的产品配置**。

如果 AI 生成的还只是概念模型，用户选择它之后，下一步应该是“匹配可提供的产品／提交配置确认”，待具体配置和报价明确后再购买。

如果它已经对应成熟模板和有效配置，则可以直接显示确定价格，进入购物车。用户不需要自己重新把柜子拆成一堆板件去采购。

**5. 确认方案 → 生成待购清单，选择这次买哪些**

用户认可整套设计，并不一定打算一次全部购买。

例如方案中有玄关柜、书桌和移动推车，用户可以选择：

“这次先买玄关柜和书桌，推车以后再买。”

因此，方案确认后应该得到一份待购清单，列出具体家具、配置、数量、价格及尚待确认的事项。用户选择本次购买的项目，再加入购物车。

**方案保存的是整个家的计划；购物车保存的是这一次准备成交的部分。**

**6. 购物车 → 确认交付 → 支付 → 订单**

到了购物车，核心选择应该已经明确，用户主要检查：

- 买的是哪几件、什么配置、各几件；
- 商品金额及适用的配送、安装费用；
- 收货信息、可提供的交付安排；
- 最终付款金额。

下单时保存一份确定的配置记录。之后用户继续修改房间里的设计，也不能悄悄改变已下单的家具。

订单再承接付款、备货或生产、配送、安装等实际状态；对应家具在项目里标记为已下单或已交付，避免重复购买。

**用你的服务举一个完整例子：**

用户通过 Quiz 表达“玄关很乱，需要收纳，但不能挡路” → 确认需求 → 系统推荐一个模块化玄关柜 → 放进用户房间，与已有鞋架和门的位置一起查看 → 用户调整柜子尺寸、板件颜色和配件 → 选择采用这个柜子，并保留已有鞋架 → 确认产品配置与价格 → 从待购清单加入购物车 → 确认配送安装并支付。

这些页面之间始终传递的是**同一个项目、同一件家具及其配置**。用户前面做出的选择，会逐步成为后面购买的依据；返回修改时保留已有内容，并重新确认受影响的配置和价格。

这些情境对应的交互规则可以统一下来，不需要做七套独立流程：

- **一个持续可访问的 Eva 入口**，用户换页面时，对话和项目进度保留。
- **一个清楚、可修改的当前范围**，例如“新家／卧室／模块柜”，系统通常自动确定。
- **轻问题就在当下回答**；用户主动想完整探索时，再展开完整 Quiz，结束后返回原来的挑选位置。
- **浏览、收藏、试摆和决定使用不同状态**，通过自然操作区分，不让用户填写分类。
- **默认自动保存，修改尽量可撤销**；需要影响已确认方案或交易时才正式确认。
- **主动建议控制在眼前的一件事上**，用户不接，也能继续自己浏览。

我会用这个标准检查每一个交互：**用户做完这一步，是更接近想清楚、挑好或买到家具，还是只是在替系统补资料？**后者应该尽量由上下文和已有操作解决。

|---|---|---|
| 1 | **Projects 列表页**，在“新家”上点「继续」 | 回到上次工作的房间和方案，而不是空白 Canvas。 |
| 2 | 看到“上次保留了两个柜子”，点「继续比较」 | 打开这两个候选，恢复各自配置。 |
| 3 | 我说“左边这个吧，颜色换浅一点” | Eva 预览修改后的配置。 |
| 4 | 点「采用并列入待购」 | 更新当前方案和待购清单。另一件保留为未采用候选，或由我移除。 |
| 5 | 点「待购清单」，只选柜子，不选推车 | 柜子进入本次购物车；推车继续留在项目里。 |
| 6 | **Cart** 点「去结算」 | 进入 **Checkout**，确认配置、收货、配送／安装及总价。 |
| 7 | 完成支付，点「返回新家项目」 | 返回项目，对应家具显示已下单，并能打开订单。未买的家具仍可继续挑。 |

如果第 1 步回来时，我想做别的，直接选择其他房间或家具即可。系统不强迫我完成上次比较。

---

**对于“Quiz 到底在哪”，我会明确做成下面这个规则：**

| 用户从哪里开始 | Quiz 出现在哪里 | 做完后去哪里 |
|---|---|---|
| 首页主动找方向 | 独立 Quiz 页 | 本次结果页，再选看家具或开始房间方案 |
| Project／房间主动测评 | 同一套 Quiz 页，自动带入项目和房间 | 回到来源项目／房间，选择是否预览 |
| 与 Eva 交流时只缺几个判断 | 当前页面的 Eva 对话内，直接点选 | 留在当前页面，继续讨论或操作 |
| 需要更完整地探索 | 从 Eva 点「完整测评」，进入 Quiz 页 | 返回发起测评的位置，带回本次结果 |
| 查看或重做过去的测评 | Project 内的测评记录入口 | 打开旧结果，或创建新一轮；旧结果不被覆盖 |

最后，页面跳转时必须一起保留三样东西：**我正在处理哪个项目和对象、我刚才做到哪里、这次测评或推荐为什么出现。**这样用户从 Quiz 到商品、从商品到 Canvas、再到购买，感受到的是同一件事继续往下做。


================ 第 19 轮 ================

用户
study case也不够 以及用户使用的时候可能有什么迷惑/感觉体验很奇怪的地方？


助手
前面的案例大多是假设“用户理解每个按钮，并且顺着流程完成”。真正需要检查的是：**用户半途改变主意、误解系统、忘记之前做过什么，或者 AI 理解错的时候，整个体验还能不能接得上。**

而且，我前面的方案本身也有问题：**“保存候选 → 采用方案 → 列入待购 → 加入购物车”这样的连续操作，可能把一次简单选择拆得过于繁琐。**

下面做一次更具体的用户认知走查。**这些是待验证的使用情境和风险假设，不是真实用户测试结论。**检查重点包括系统状态是否清楚、能否撤销，以及 AI 出错后是否容易纠正，参考了 [NN/g 的可用性原则](https://www.nngroup.com/articles/ten-usability-heuristics/)和 [Microsoft 的人机交互指南](https://www.microsoft.com/en-us/research/project/guidelines-for-human-ai-interaction/)。

**1. 我从广告进入测评，做完后突然被要求注册**

**点击路径：**  
首页 →「找找适合的家具」→ Quiz → 完成 →「查看推荐」。

**我可能怎么想：**

> “我花了这么久回答，为什么现在必须注册才能看？”  
> “如果返回，刚才是不是白做了？”

**页面和 Eva 应如何处理：**

- 直接展示本次结果和初步推荐，不能在这里突然锁住结果。
- 未登录时，明确区分“已保存在此设备”和“已保存到账户”，不能笼统显示“已保存”。
- 我点「保存，稍后继续」时，再说明登录可以跨设备继续。
- 登录成功后回到**原结果页的原位置**，保留本次答案、推荐和选中的家具，不能落到空白账户首页。

这里最容易破坏体验的不是注册本身，而是**注册打断了已经投入的探索，而且不知道内容是否还在。**

**2. 我在图片测评里选了一个房间，但只是喜欢它的书柜**

**点击路径：**  
Quiz 图片题 → 选一张深色客厅图 → 结果页 →「看家具」。

**我可能怎么想：**

> “我只是喜欢那面书柜，为什么现在推荐的都是黑色家具？”  
> “为什么它说我喜欢工业风？”

**应如何处理：**

- 结果不能把整张图的所有特点都算成确定偏好。
- 结果页显示具体、可纠正的推断，例如“这次可能偏向木质、开放收纳”，而不是只给一个风格标签。
- 当这个推断明显影响下一轮推荐时，Eva 可以问一次：“这张图里，你主要喜欢书柜、配色，还是整体感觉？”
- 我点「书柜」后，推荐随之调整；不用重做整个 Quiz。
- 商品列表允许「换个方向」或取消本次测评条件。

**AI 必须区分“我点了这张图”和“我赞同图里所有设计”。**

**3. 我不知道尺寸，只想先看看，系统却一直问**

**点击路径：**  
项目页 → 客厅 →「帮我找一个柜子」→ Eva 询问尺寸。

**我可能怎么想：**

> “我现在在地铁上，又没法量。”  
> “是不是不填完就什么都不能做？”

**应如何处理：**

问题旁给出实际可用的选择：

- 「输入尺寸」
- 「大概知道」
- 「先看款式」

我点「先看款式」后，直接进入推荐或商品列表，当前方案标明尺寸尚未确认。

之后我点某个柜子的「放进房间」，可以使用明确标注的示意空间；不能把估算尺寸表现成实测结果。

到我选择「购买这件」时，再针对这件商品提示需要确认的尺寸。**未知信息可以暂存，不能偷偷用默认值把未知变成已确认。**

**4. Quiz 说我适合一种风格，但我完全不认同**

**点击路径：**  
Quiz → 结果页 → 看见“你的方向偏简洁、浅色”。

**我可能怎么想：**

> “这不像我。”  
> “是不是我的题答错了？要全部重来吗？”

**应如何处理：**

结果页至少有两个直接操作：

- 「这个方向不太对」
- 「看看其他方向」

点「不太对」后，Eva 只问“主要哪里不对”，让我点颜色、材质、家具类型、整体感觉，或直接说。

我说“我喜欢木头，但不喜欢这么素”，系统保留木质方向，增加更丰富的候选，而不是清空所有答案。

这次结果仍可保留在历史中，但标记为未采用。**不认同结果应该是一种正常反馈，不应让用户觉得自己测评失败了。**

**5. 我重新做了测评，结果不同，却不知道哪一个正在生效**

**点击路径：**  
客厅 Canvas →「换个方向」→ 新 Quiz → 新结果 → 返回 Canvas。

**我可能怎么想：**

> “我刚做完，怎么房间没变化？”  
> 或者：“怎么我之前辛苦选的东西全变了？”

这两种情况都可能让人困惑。

**应如何处理：**

- 测评完成时清楚说明：“新方向已保存，当前房间还没有改变。”
- 主要按钮是「预览到客厅」。
- 点击后进入可撤销的预览，明确显示正在预览另一方向。
- 「用这个方向」才改变当前方案；「返回原方案」恢复原状。
- 后台保留过程记录，不要求每次给版本起名字。
- 只有用户想长期保留两个方案比较时，才提供「保留两个版本」。

这样用户能区分**做出了一份新结果、看到了新预览、决定采用**，但不用管理一堆版本文件。

**6. 我点了“喜欢”或心形，系统却把家具放进房间了**

**点击路径：**  
商品列表 → 点击心形 → 返回 Canvas。

**我可能怎么想：**

> “我只是收藏，为什么房间里多了一件？”  
> “是不是每收藏一个就算我要买？”

**应如何处理：**

几个核心动作必须有稳定含义：

| 操作 | 实际含义 |
|---|---|
| 收藏 | 留着以后看 |
| 放进房间 | 加入当前空间试摆 |
| 替换这件 | 用新家具替换明确选中的物件 |
| 加入购物车 | 按当前有效配置准备购买 |

收藏不自动放置；试摆不自动加入购物车。

如果我正在选客厅柜子，收藏可以默认附带当前项目来源，但这只是方便之后找回，不能被解释为“已采用”。

**7. 我从测评结果去看商品，再回来，原来的讨论不见了**

**点击路径：**  
客厅测评结果 → 推荐柜子 → 商品详情 → 查看配色 →「放进房间」。

**我可能怎么想：**

> “现在还是在刚才那个客厅里吗？”  
> “为什么 AI 又问一次预算？”  
> “我想回去看另外两个推荐，去哪找？”

**应如何处理：**

- 商品详情保留来源入口，例如「返回客厅推荐」。
- 「放进房间」已经有明确来源时，直接使用这个客厅，不再弹项目选择。
- Eva 继承这次选择所依赖的需求和对话，不重复问已知信息。
- 返回商品列表时恢复筛选和浏览位置。
- 从 Canvas 返回推荐时，原候选仍然存在，不重新生成一批替代。

对用户而言，**换了页面不应该像换了一个服务人员。**

**8. 我同时打开两个项目，AI 把内容改错地方**

**点击路径：**  
浏览器标签 A：新家／客厅。  
浏览器标签 B：妈妈家／卧室。  
我在 B 中说：“把这个换成浅色。”

**我可能怎么想：**

> “我明明在看妈妈的卧室，为什么新家的柜子变了？”  
> “这个 AI 到底知道我在哪吗？”

**应如何处理：**

- 每个页面和对话操作都绑定自己的项目、房间和选中对象，不能只依赖账户最后打开的项目。
- Eva 给出的操作明确指向对象：“预览妈妈家卧室这件柜子的浅色版本。”
- “这个”没有清楚指向时，才要求我点选对象。
- 如果我说“全部换成浅色”，而范围可能是整柜、全房间或整个项目，必须先明确范围再批量修改。

这里的确认是必要的，因为理解错误会改变很多内容；不是每次换颜色都要确认。

**9. AI 生成还没完成，我已经切去别的房间了**

**点击路径：**  
客厅 Canvas →「生成摆放方案」→ 等待期间切到卧室 → 客厅生成完成。

**我可能怎么想：**

> “为什么突然把我带回客厅？”  
> “这个新方案怎么跑进卧室了？”  
> “我刚才到底有没有成功生成？”

**应如何处理：**

- 结果归回发起生成的客厅，不能应用到当前恰好打开的卧室。
- 用一个简短通知：“客厅方案已完成 · 查看”。
- 不自动切页、不自动覆盖。
- 我点「查看」才进入客厅的结果预览。
- 如果部分家具失败，保留成功部分，说明哪几件未完成，并提供局部重试。

如果生成失败，也不能让我重新回答 Quiz、重新上传同一张照片。

**10. 我手动改了家具，Eva 还在根据旧方案提建议**

**点击路径：**  
Canvas → 我拖动柜子、删除椅子 → 打开之前的 AI 建议 →「应用」。

**我可能怎么想：**

> “我刚调整的怎么又被改回去了？”  
> “AI 说椅子挡路，但我早就删掉了。”

**应如何处理：**

- Eva 提建议时，要以当前场景为依据。
- 旧建议可以保留，但不能假设它仍适用于新场景。
- 应用旧建议之前，检查相关对象是否已经变化。
- 若有冲突，明确到具体变化：“这份建议生成后，你移动过柜子。要按当前位置重新计算吗？”
- 不相关的小改动不必阻止应用，例如只改了灯的颜色。
- 撤销应恢复到本次操作前，不丢失之前的手动工作。

**建议记录可以是历史，执行动作必须针对当前状态。**

**11. 我上传了房间照片，结果很好看，却发现不是我家**

**点击路径：**  
项目页 →「上传房间照片」→ 上传 →「看看怎么改善」。

**我可能怎么想：**

> “它为什么把窗户改了？”  
> “这张图到底是效果参考，还是已经准确还原了房间？”  
> “原来的沙发还能保留吗？”

**应如何处理：**

上传后的下一步明确提供不同目的，例如：

- 「根据照片讨论怎么改善」
- 「生成改造效果参考」
- 「辅助建立房间」

不能用一个模糊的「生成我的家」混在一起。

若生成的是效果参考，就清楚标示其性质，不能拿它当准确尺寸依据。进入可编辑房间前，需要确认关键尺寸和开口。

Eva 要分清照片里“检测到一个沙发”、用户说“这是已有沙发”、用户说“我要保留它”，这是三种不同程度的信息。

**12. 房间里既有传统家具又有模块家具，我不知道哪些会被买下来**

**点击路径：**  
Canvas → 看着已有沙发、参考茶几、模块柜 →「购买方案」。

**我可能怎么想：**

> “怎么连我自己的沙发也算钱？”  
> “这张茶几只是用来搭配，为什么进购物车？”  
> “生成的柜子真的是你们能卖的吗？”

**应如何处理：**

在物件详情里明确显示它的身份：

- 已有家具；
- 参考物件；
- 可购买商品；
- 待确认的设计概念。

平时不用让我逐件填写身份，可以根据添加来源自动设定，允许纠正。

点「购买方案」后，只汇总已选择购买且配置有效的商品。概念家具单独显示需要匹配产品或确认配置，不能用一个看似准确的价格直接结算。

这里尤其不能把**模型看起来完整**等同于**商品已经确定**。

**13. 我终于选好了，却要连续点四次“确认”**

**点击路径：**  
Canvas →「保留」→「采用」→「列入待购」→「加入购物车」。

**我可能怎么想：**

> “这些按钮到底差在哪？”  
> “我刚才到底算不算选好了？”

这是我前面方案里需要直接修正的地方。

**应如何处理：**

根据用户当前目的，提供一次清楚的操作：

- 我只是看看：关闭即可，过程自动保存。
- 我想留着比较：点「收藏」。
- 我想看放进去的样子：点「放进房间」。
- 我想买：点「加入购物车」，需要时先完成具体配置。

“方案采用”“待购状态”等可以由这些操作更新，不必全部做成用户必须经过的步骤。

如果我说“这个就要了”，Eva 可以呈现具体配置与「加入购物车」，不需要再追问“是否标记为已决定”。

**14. 我在购物车里换了颜色，回到房间却还是原来的颜色**

**点击路径：**  
Canvas 中的木色柜子 → 加入购物车 → 在商品配置中换成白色 → 返回 Canvas。

**我可能怎么想：**

> “我最后买的是哪一个？”  
> “购物车和房间是不是两套独立的东西？”

**应如何处理：**

- 购物车商品保留它来自哪个项目、哪件家具。
- 修改配置时明确这是当前待购家具的修改，关联的项目物件同步反映变化。
- 如果我想买白色版，但保留木色版继续比较，可以明确选择保留为另一候选。
- 如果我是在 Canvas 中随手试白色，已经入购物车的配置不应悄悄被替换；要显示“房间预览与购物车配置不同”，允许一键更新或恢复。
- 下单后固定订单配置。之后再修改项目，只产生新的设计状态，不修改已成交内容。

**“正式修改待购配置”和“随手试一个颜色”必须有不同的操作含义。**

**15. 我和伴侣分别做测评，结果冲突**

**点击路径：**  
同一个项目 → 邀请伴侣参与 → 两人分别完成测评 → 查看房间建议。

**我们可能怎么想：**

> “为什么她做完之后，我的结果没了？”  
> “AI 说‘你喜欢深色’，这个‘你’指谁？”

**应如何处理：**

- 每份结果记录是谁做的、针对哪个房间。
- 展示共同点和不同点，不把两个人混成一个偏好档案。
- Eva 可以提出：“两位都喜欢木质，但配色方向不同，要看看折中的方案，还是各保留一个？”
- 两人共同采用的方案，与各自的探索分开。
- 如果只是把设备交给伴侣临时试一次，需要有简单的「替别人探索」入口，不必强迫对方先注册才能看看。

这个情境会直接检验：系统究竟是在理解家庭决策，还是只会维护一个不断被覆盖的“用户画像”。

**16. 我几周后回来，价格、库存或我的想法都变了**

**点击路径：**  
Projects → 新家 →「继续」→ 打开之前的候选或购物车。

**我可能怎么想：**

> “为什么价格不一样了？”  
> “我记得那个柜子在哪里？”  
> “为什么还坚持按我几周前的预算推荐？”

**应如何处理：**

- 恢复上次内容，先让用户认出自己做到哪里。
- 只突出有实际影响的变化：价格变化、商品不可用、配置需要重新确认。
- 不悄悄把旧商品替换成别的，也不直接删除历史候选。
- 我修改预算后，Eva 使用新预算继续推荐；已有选择保留，标明是否超出当前范围即可。
- 未完成的问题不会变成一串必须处理的通知。

长期陪伴的感觉来自“理解我们走到哪里、哪些事情发生了变化”，而不是不断提醒我还有多少任务未完成。

---

**从这些案例看，你最需要消除的几种“奇怪感”是：**

| 用户的疑惑 | 背后的问题 |
|---|---|
| “它现在在帮我做哪个房间？” | 当前作用范围不明确 |

你的网站可以保留复杂的 Project、记忆、方案和版本机制，但在用户面前，最常见的操作应当仍然是：**看看、问问、试试、留下、换掉、买下。**每个动作影响什么、保留什么，以及能否返回，都需要明确且一致。

用户

**对，同一个用户进入 Playground 时，可能带着几个尚未理清的想法。系统需要让这些想法同时存在，允许他来回看、分别推进，之后再决定它们是组合起来，还是择一采用。**

而且，“多个想法”不一定都是完整方案。可能是一种风格、一件家具、一个生活需求，或另一个家的计划。不能每提到一个想法，就让用户新建 Project。

**1. 我进入 Playground，直接把几个想法一起告诉 Eva**

Eva 不应该马上把三个需求塞进一张生成图，也不必要求我先选择一个才能继续。

它可以在当前对话里整理成三个可点击的内容：

- **客厅：试一个阅读角**
- **客厅：看看办公位置**
- **卧室：重新考虑衣柜**

并说：

> “这几个想法都留在新家项目里了。阅读角和办公位置可以分别试，也可以之后看看能否兼顾。”

**我点「阅读角」→ 当前 Canvas 定位到客厅，Eva 针对阅读角继续。**另外两个想法保留为尚未展开的记录，不需要现在回答问题，也不需要立即生成方案。

这里保存的首先是“我想研究这件事”，还不是一套设计。

**2. 我做着阅读角，突然想到另一种客厅布置**

这时，两个想法已经涉及不同的空间安排。

具体操作应该是：

1. Eva 提供「另试一版」，说明将保留现在的阅读角。
2. 我点它，系统从当前客厅复制一个尝试版本。
3. 当前 Canvas 显示新版本，开始尝试大桌子。
4. 工作区里能找到两个清楚的入口：「保留沙发＋阅读角」「大桌子方案」。
5. 我点击其中一个，就查看那一版，不需要新建项目或新开聊天。

**用户可能觉得奇怪的地方：**

> “我刚说了另一个可能，原来的东西怎么没了？”  
> “我切回去，AI 还在按大桌子的思路改阅读角？”

因此，切换版本时，**场景、选中对象和 Eva 当前讨论的对象要一起切换**。共同的房间尺寸可以沿用，各版本的决定需要分别保留。

**3. 我没有要两套客厅，只是想比较两张椅子**

**我的操作：**

在阅读角方案里 → 打开家具库 → 看中椅子 A → 又点开椅子 B。

这种情况不值得生成两个完整的房间方案。

更自然的是：

1. 我点椅子 B 的「替换预览」。
2. 同一个位置临时显示 B。
3. 我可以切换「椅子 A／椅子 B」查看。
4. 点「用这张椅子」，才确定当前配置。
5. 点「两个都留着」，就保存为这个阅读角的两个候选。

这里需要分清：

- **两张椅子都想买来搭配**：点「加入房间」。
- **两张椅子二选一**：点「替换预览／比较」。

如果两种操作都用一个「＋」，用户很容易发现房间里堆满家具，却不知道怎样表达“我只是比较”。

**4. 我喜欢方案 A 的布局，也喜欢方案 B 的柜子**

**我的操作：**

打开「大桌子方案」→ 点击柜子 → 对 Eva 说：

> “把这个柜子放到阅读角那版看看。”

接下来的流程应该是：

1. Eva 明确识别当前选中的柜子和目标版本。
2. 我点「在阅读角方案预览」。
3. 系统打开阅读角方案，把这件柜子放进去预览。
4. 如果与原书架占用同一位置，询问「替换书架」还是「另外找位置」。
5. 我确认后，更新阅读角版本；大桌子版本保持原状。

**容易奇怪的地方是：**

> “为什么带过去的时候，连另一套房间布局也带过来了？”  
> “为什么复制柜子后，两个方案里的柜子一起变色了？”

默认应该复制当时那件家具的配置，之后分别编辑。只有用户明确要求联动，才让多个版本一起变化。

**5. 我只是随手记下灵感，还不想做任何设计**

我正在改衣柜，突然说：

> “以后也许可以在客厅加一个咖啡角，先记着。”

Eva 应该简单回应：

> “已留在客厅的想法里，之后可以继续。”

**页面不跳转、不切换房间、不启动生成。**

之后，我从项目内的「想法」入口点击“咖啡角”，再点「开始试试」，才进入对应房间展开。

这点很重要：**记录想法是一种完整有效的操作，不需要立刻把它推进成任务、测评或模型。**

如果每记一个念头，AI 都追问预算、尺寸和风格，用户以后就不愿意随手告诉它了。

**6. 我下次回来，可能想接着做另一个想法**

假设我上次最后编辑的是衣柜，但今天想看阅读角。

| 维度 | 回答的问题 | 示例 |
|---|---|---|
| 实际身份 | 这件东西和用户是什么关系？ | 已有家具、考虑购买、纯参考、已下单 |
| 模型来源 | 这个模型从哪里来？ | Furnishes 商品库、用户导入、AI 根据照片生成、AI 创作 |

| 类型 | 用户怎么操作 | 保存规则 |
|---|---|---|
| 当前工作稿 | 正常编辑即可 | 自动同步，持续更新到最新状态 |
| 保存的想法 | 点「保存这个想法」，可命名 | 固定当时的状态，后续编辑不覆盖 |
| 项目副本 | 点「复制项目」 | 建立独立 Project，之后分别修改 |

- 保留沙发的版本；
- 大桌子版本；
- 低预算版本。

**6. “回去看看”和“从旧版继续改”，必须分清**

这是你要求里最容易被做错的部分。

假设：

- 保存的想法 A：阅读角；
- 保存的想法 B：大桌子；
- 当前工作稿 C：我刚刚调整好的最新内容。

我点 A 时，应该进入：

> **正在查看：阅读角**  
> 「返回当前工作稿」　「从这里继续」

此时：

- A 显示出来；
- C 仍然存在；
- 自动同步不能把 A 写回去覆盖 C；
- 我可以切换到 B，再返回 C；
- 查看旧版本不会删除新版本，也不会重新生成一次。

**如果我点「从这里继续」并准备修改 A，就需要处理原来的 C。**

因为“只有一个最新工作稿”与“原工作稿永远能找回”之间，需要一个明确的保留动作。可以提供：

- **留在当前项目继续**：先把 C 保留为一个想法，再以 A 为新的工作稿起点。
- **复制为新项目继续**：原项目和 C 完整保留，在副本中编辑 A。

若手动存档已满，就在这个动作上处理保存位置，不能直接覆盖 C。

这样用户不必理解技术上的版本历史，但能明确知道：**看旧版不会丢内容，继续改旧版之前也会保留当前成果。**

**7. 存档要保存“这份想法”，不只是保存一张截图**

需要保存的内容包括：

- 房间几何、尺寸、门窗；
- 家具位置、朝向、配置、板件和材质；
- 哪些是已有家具、待购物件或参考模型；
- 哪些物件锁定；
- 这版方案采用的需求与限制；
- 用户保存的动线或重要查看位置。

聊天记录仍属于项目，可以关联到当时的版本；查看旧版不应把之后的聊天删除，也不应倒退用户整体的长期记忆。

已下单的订单同样独立保留。回看一个旧设计，不会撤销订单或改变已购买配置。

**8. 复制项目，让几个想法可以彻底分开发展**

用户点「复制项目」后，需要明确复制的是哪份内容：

- 正在编辑工作稿：复制当前工作稿；
- 正在查看旧想法：按钮明确写「将此想法复制为新项目」。

副本带走房间、家具配置、身份信息和相关需求，并保留“从哪个项目／想法复制”的来源。订单可以作为来源信息引用，但不能被复制成新的订单。

这样用户可以在同一个项目里保留小范围比较，也能在两个方向差异很大时分开发展。

把这些串起来，一个具体操作就会是：

**进入客厅 → 多选书桌和书柜 → 让 Eva 调整办公区 → 显示门口到书桌的动线 → 第一人称走一遍 → 返回整体视角 → 手动保存“办公区方案” → 继续尝试阅读角 → 点回办公区检查 → 返回最新阅读角 → 必要时复制项目分别继续。**

这一整段过程中，用户始终能看清三个信息：**当前是哪一版、正在操作哪些东西、改动保存到哪里。**

- 用户想“找个东西放进房间”，可以在「添加」里找到目录、收藏和可添加的生成结果。
- 用户想“看看之前试过什么”，可以在「想法」里看到生成候选及其讨论背景。
- 两个入口可以引用同一份结果，状态保持一致，不用生成两套互不关联的数据。

**哪些东西可以浮起来，哪些应该固定**

我会给浮动界面三个明确规则。

**第一，短操作跟着对象，复杂操作有固定展开位置。**

点中柜子，附近出现「调整／问 Eva／复制」足够了。尺寸、材料、板件列表、商品详情需要一个稳定的详细区，避免随着柜子旋转、镜头移动到处跳。

详细区可以悬浮在画布上、可以收起，展开位置保持一致。因此，保留开放画布也能获得正式工具的秩序感。

**第二，参考内容允许钉住，工具默认自动安排。**

用户正在对照一张参考照片，可以点「钉住参考」，让它留在场景旁边。

同时打开家具库、属性、拼装、历史、测评五六个窗，会让用户开始花精力整理界面。建议普通工具区一次展开一个主要任务，Eva 可按需并存；窄屏时切换显示，并保留输入、筛选和滚动位置。

**第三，进入复杂任务时，替换当前工具。**

进入「查看拼装」，同一画布暂时聚焦家具，工具变成步骤、播放、上一步、下一步、返回房间。

进入「第一人称」，显示走动提示和退出入口。

进入「编辑房间」，显示墙体和门窗工具。

这样每个任务都能拥有足够空间，而且用户知道如何回来。

**具体走一遍，你的用户会看到什么**

假设用户已经在客厅 Playground，想试一个现成柜子，又想让 AI 帮忙调整。

1. **点「添加」→「现成家具」。**  
   家具浏览区打开，房间仍然可见。点商品卡查看详情，点「放进房间」才进入放置状态。

2. **柜子放好后自动选中。**  
   柜子有清楚的轮廓高亮，短操作条显示「调整／问 Eva／复制」。商品详情里能看到尺寸、价格、板件组成。

3. **点「问 Eva」。**  
   输入区出现明确的对象标签：`客厅 · 玄关柜 01`。用户说“这个再窄一点”，指向已经可见。

4. **用户还想同时改旁边的架子。**  
   点「多选」再点架子，或者使用快捷键。两件一起高亮，输入区显示 `已选 2 件`，可展开查看或移除其中一件。选区在发送时固定，后续转动镜头不改变这条请求的对象。

5. **AI 给出两个选择。**  
   对话里展示简短差异和预览入口。用户能「预览」「应用」「留作备选」。保留的候选进入这个项目的想法集合，不要求用户当场决定。

6. **用户想确认结构。**  
   选中柜子 →「组成与拼装」→「查看步骤」。房间暂时让位于家具演示，完成后回到原来的房间位置和视角。

7. **用户想知道会不会挡路。**  
   点「动线」，选择“门口到沙发”，画面叠加路线；相关问题出现在路线附近，详细解释按需展开。再点「第一人称」，从人的视角看实际摆放。

8. **用户喜欢这个方向，但还想试另一个。**  
   点「保存方案」，命名“窄柜方案”。然后继续调整，最新工作稿自动同步。之后查看“窄柜方案”时，界面明确标为预览，并保留「返回最新工作稿」。

这条过程中，用户一直围绕自己的房间前进，每一步出现的功能都和眼前的问题有关。

**怎样让用户容易理解，而不会觉得“功能都藏起来了”**

你需要把以下信息直接展示出来：

- **入口使用动作名称。**「添加家具」「编辑房间」「查看动线」比只写 Catalog、Tools 或陌生图标更容易理解。
- **选中后说清楚选中了什么。**「玄关柜」「玄关柜 › 左侧板」「已选 3 件」要有明显区别；单击默认选整件，进入「编辑板件」后再选局部。
- **当前任务有名称和退出按钮。** 始终能看到“正在编辑房间”“正在查看拼装”“正在预览旧方案”。
- **预览、应用、保存分别表达。** 点击缩略图只负责查看；改变房间需要明确的应用动作。
- **AI 的讨论范围可见、可改。** 可以是当前房间、选中的家具、某个备选想法；测评也显示“这次针对客厅”，避免被理解为给用户永久定性。
- **关闭界面保留进度。** 收起商品浏览后，再打开仍停在之前的搜索结果；收起 Eva 后，未发送的话还在。
- **空状态给与当前任务有关的下一步。** 空房间提示添加家具；已选家具提示可调整、询问或查看组成，不必展示一整套教程。

对你来说，最值得优先借鉴的是 **Miro / Excalidraw 的稳定工具入口、Spline 的对象层级、Recraft 的明确 AI 作用范围，以及 Milanote 的多想法组织方式**。这些可以组合在同一个开放式 Playground 里，分别解决你不同类型的功能需求。

**具体来说，我会修改前面的方案，让房间本身成为主要入口。**

用户进入已有项目后，主要看到：

- 自己的房间。
- 可以展开的家具浏览区。
- 随时能说话的 Eva。
- 小而稳定的项目、方案、视角和购买入口。

其中，**家具浏览区可以是贴在底边、能收起的一块连续区域**。这里是一个具体设计方向，不代表这些参考产品全部采用相同布局。用户浏览时保持房间可见，也不用整理多个浮窗。

更重要的是，这块区域会根据用户的动作展示对应内容。

**例如，用户想把柜子换得好看一点，应该这样发生：**

1. **点房间里的柜子。**  
   柜子高亮，附近直接出现颜色选择，以及「换款」「改组合」「⋯」。价格和商品名简短显示。常见操作不再需要先点一次“打开属性”。

2. **点颜色，房间里的柜子立即变化。**  
   可以连续点几种颜色比较，保留撤销。每次换色都弹出“预览—应用—确认”，会很累。

3. **点「换款」，家具浏览区直接变成这件柜子的替换候选。**  
   用户点不同商品，就在原位置试摆。浏览期间保留原款，点「用这款」结束试换，点取消恢复。无需先删除、重新找目录、再摆一次。

4. **点「改组合」，才进入模块层级。**  
   镜头适当靠近，明确提示“选择要修改的板件或模块”。选中层板后，展示适用颜色、样式和允许的组合选项。完成后回到整件家具。

5. **直接对 Eva 说：“这件窄一点，但收纳不要少。”**  
   输入区已经带着这件柜子的对象标签。用户不需要先点“问 AI”、再重新解释自己在说谁。

这里用户的注意力一直留在柜子上。颜色、商品、模块、AI 是几种修改它的方法，界面随着动作衔接。

对于真实可购买的模块家具，尺寸调整要落到你允许生产的规格和组合上；拖动时可以吸附到有效尺寸，并同步更新配置和价格。这样直接操作也能对应真实商品。

**你其他的功能，也应该接在这些行为上，而不是要求用户额外走一套流程。**

| 用户正在想什么 | 对应交互 |
|---|---|
| “这边空着，放点什么？” | 从家具浏览区挑选；也可以选中这片区域，让 Eva 推荐。推荐位置可临时出现提示，用户能自由移动。 |
| “这几件要一起协调。” | 多选后一起高亮，Eva 显示“针对这 3 件”；直接提供适用于多件的调整操作。 |
| “我不知道为什么这里总是很乱。” | 直接问 Eva；需要补充信息时，在对话里出现几个可点选的问题，也能自由回答。测评结果附着于这次房间讨论。 |
| “这个会不会挡路？” | 拖动时显示相关间距或冲突反馈；点击提示展开动线，详细检查也有稳定入口。 |
| “站在里面是什么感觉？” | 点「进去看看」，选起点进入第一人称；退出后返回刚才的编辑视角。 |
| “它到底有多少片，怎么装？” | 在这件家具的详情里展开组成和拼装演示，结束后回到它在房间中的状态。 |
| “这个方向不错，我还想试另一个。” | 点「留住这个方案」，出现缩略图；继续调整，最新工作稿自动同步。旧方案与新工作稿都能回来。 |
| “这几件我想买。” | 选中商品加入购买清单；清单汇总用户确认购买的配置。摆进房间本身不等于决定购买。 |

**AI 也要参与这个连续过程，不能要求用户频繁切换到聊天工作台。**

例如，用户把柜子拖到门边，Eva 可以在相关位置出现一条简短提示：

> 柜子可能影响开门。试试更浅的款式？

点一下，家具浏览区就展示更浅的候选；用户仍在看自己的房间。只有用户想讨论原因、需求或者多个方案时，才展开完整对话。

同样，用户说“我还有另一个想法”，AI 可以帮助保留当前方案并开始探索，但不必要求用户理解“全局偏好、项目记忆、临时假设”的内部分类。界面只需要表达清楚：“这次先为客厅试试”“这个想法已保留”。长期偏好的推断则不能因为一次尝试就固定下来。

**我前面还需要改掉一个过度设计：把所有动作都做成预览和确认。**

应该按动作的影响区分：

- **换色、移动、旋转等小调整：**即时反馈，可以撤销。
- **连续试换商品：**进入一次试换，期间随意比较，最后保留或取消。
- **AI 重排整个房间：**展示改动或前后比较，再应用。
- **查看旧方案：**明确处于查看状态，始终保留回到最新工作稿的入口。

这样用户既能放心尝试，也不用每点一下都完成一段流程。

所以我会调整之前的方向：**默认界面围绕“挑、摆、换、看看效果”组织；复杂功能贴着当前对象和当前问题出现。** 最终是否直觉，仍要用具体任务验证——例如让第一次来的用户独立完成“换一件柜子、改一块板、保留两种想法”，观察他在哪里开始寻找按钮或担心丢失结果。仅仅把功能分组整齐，还不足以证明好用。

**2．DecorMatters：最值得学的是“从房间里的需求，直接进入相关商品”。**

我进入了它的实际网页编辑器和设计详情页，也读了完整设计工具帮助页。

它包含商品分类与搜索、上传自己的背景、收藏与自有素材入口、设计保存与导出、社区发布和挑战。对象编辑工具包括角度图、翻转、前后图层、复制、锁定、裁切、亮度、透视和去背景。[官方设计工具说明](https://decormatters.com/help-center/designing/design-tools)

实际编辑器是**顶部固定操作栏 + 左侧可隐藏的商品区 + 大面积房间图像**：

- 顶部：Return、Undo/Redo、Zoom、View、Recenter、Export、Save、Post。
- 左侧：分类、搜索、商品缩略图。
- 商品区边缘：Shop、Effect、Wishlist、MyDecor、Inventory 等入口。
- 房间内部：新手引导直接指向可操作的位置。

我实际遇到的教程不是一长串说明，而是：

> 点击房间里的 Lighting → 左侧直接筛选为 Floor Lamps。

![DecorMatters 从场景入口筛选灯具目录](/Users/mohanlu/.codex/visualizations/2026/10/02/01a0fdb0-2827-7352-b52a-44d15e02f65b/decormatters-editor.jpg)

**这对你比“加一个商品 tab”更有价值。**

例如用户点床边空位，或告诉 Eva“这里想放床头柜”：

1. 房间保持当前位置。
2. 商品区打开，并已经筛选床头柜。
3. 优先呈现适合该空间尺寸的模板。
4. 点商品即可试放。
5. 选中试放家具后，再出现颜色、尺寸、组成、拼装说明。

用户不用离开房间，去商品列表重新开始搜索。

它的设计详情页还有 `Items in Design`：效果与使用的物品放在一起。这能迁移成你的“这个方案用了什么”，并支持逐件查看、收藏或购买。

**需要避免两类混淆。**

第一，它当前这套编辑工具包含很多二维拼贴操作。前后图层、透视拉伸、切换产品角度图，并不能证明家具在真实三维空间中放得下。你的家具应该通过真实模型的位置、尺寸和旋转操作。

第二，编辑器里的 Shop、Purchased、虚拟币，与实体家具购买不是天然同一回事。你需要让“收藏素材”“放入房间”“加入购买清单”有清晰区别，不能用一个模糊的“已拥有”覆盖它们。

游戏挑战和奖励适合鼓励探索，但不宜占据你真实购买流程的核心位置。

---

**3．Moodroom：对你的 Project、多个想法、逐步决定和购买衔接，参考价值比首页看起来更大。**

实际登录应用比公开演示丰富。左侧已经有：

> Overview、Floor plan、Rooms、Moods、Catalog、Procurement、Spec Book、Bill of Quantities。

我还实际检查了 Moods、房间方案、采购页、助手，以及 2D/3D Playground 入口。

**它对“多个想法”的处理值得你认真参考。**

Moods 页面明确解释：一个 Mood 是针对整个住宅的一次风格方案，可以选择其中哪些房间生成，再继续迭代。因此它不是“这个人永久属于北欧风”，也不是“一个房间只能有一个结果”。

在具体房间方案里，又有：

- 参考照片。
- 当前 Mood 名称。
- 迭代次数。
- `Iterate on this design`。
- `Mark as final`。
- 该房间的物品清单。
- `Shop this render`，寻找与画面匹配的真实产品。

官网也将房间效果、商品选择、备注和版本历史放在同一个项目中。[Moodroom 产品说明](https://www.moodroom.ai/)

**它的下一步入口使用的是用户目的。**

效果图下面直接有三个选择：

- `Explore in 2D & 3D`：移动家具、尝试尺寸、研究布局。
- `Find your perfect piece`：添加或替换真实家具。
- `Fine-tune the feeling`：描述修改，创建下一版。

这比把“模型库、参数、生成器、渲染器”放在用户面前更容易理解。

**采购衔接也有明确规则。**

我打开 Procurement，页面说明：房间设计被标为 Final 后，相关物品才会进入采购，随后追踪订购和交付。

这解决了“随手尝试的东西是否都算准备购买”的问题，但对你的业务不能直接照搬。你的用户可能只确定了玄关柜，客厅还在探索。

因此 Furnishes 应该允许：

> 确定这件家具 → 加入购买清单。

无需先把整个房间或整个方案标记完成。

**它最重要的局限，我在实际界面里看到了明确提示。**

进入 Room Playground 后，产品说明：

- 房间比例和家具位置是可编辑的估计值。
- 不是效果图的精确重建。
- 不保证实际适配。
- 布局保存在当前设备，房间记录保持不变。

本次浏览器的 3D 显示不可用，我检查了它提供的 2D 模式。[本次 Playground 截图](/Users/mohanlu/.codex/visualizations/2026/10/02/01a0fdb0-2827-7352-b52a-44d15e02f65b/moodroom-playground.jpg)

**这揭示了你的关键要求：房间效果、实际布局、商品配置和保存版本必须连起来。**

用户不能在 Playground 把柜子缩小了，回到商品清单却还是原尺寸；也不能在另一台设备打开项目，效果图还在、布局却没了。

另外，Moodroom 右下角确实有助手，但我打开后看到的是通用帮助开场与“怎样开始项目、Project 和 Version 有什么区别”等问题。我没有验证它能否针对选中的家具进行修改，也没有证据说明它具备你要求的长期与临时记忆区分。

---

**4．RoomAI：最值得学的是快速开始和视觉化选择，但它主要围绕图片结果工作。**

我检查了实际生成表单，选择过示例图，打开了风格选择器并切换风格。生成按钮要求登录，因此没有验证生成质量。

页面由三个区域组成：

- 左侧：各类房间工具、Assets、Pricing。
- 中间：输入照片、生成选项。
- 右侧：前后对比示例。

表单提供房间类型、风格、补充文字、参考图、Fast/Best、比例和输出数量。通用房间页有自动识别类型和自动风格选项。官方还描述了连续修改和使用已有家具照片作为参考。[RoomAI 功能与操作说明](https://www.roomai.ai/ai-room-design)

**它两个很好的减负设计：**

一是没有照片也能用示例开始，用户可以先理解产品，而不是立即被要求上传。

二是风格通过图片选择。点击当前风格 → 打开视觉选择器 → 点选风格 → 返回原表单，已选内容更新。[实际风格选择器截图](/Users/mohanlu/.codex/visualizations/2026/10/02/01a0fdb0-2827-7352-b52a-44d15e02f65b/roomai-style-picker.jpg)

你的 quiz 可以借鉴这种**小范围、视觉化的选择**。比如用户说“我不知道喜欢什么”，Eva 当场给三个明显不同的方向，再根据选择继续；不用先完成一份完整风格问卷。

**但它也展示了你应避免的问题。**

生成表单中有不少参数。对于“我想让玄关不乱”的用户，比例、输出张数和画质并不是此刻最重要的决定。

我选择输入示例时，右侧仍然有独立的营销对比图。这样的布局容易让人误以为右边就是当前输入的结果。你的页面必须清楚区分“示例”“正在预览的方案”和“已经应用到项目的布局”。

此外，参考图中的家具被画得相似，不等于系统已经拥有该家具的真实尺寸、型号、板件和库存。它适合帮助用户找感觉，不能替代你的模块配置与购买依据。

---

**5．Coohom：最值得学的是清晰的任务输入和结果比较，但这里看到的是 Demo。**

我检查了 Interior Design 和 Floor Plan 的工作区，也读了 Furniture & Materials 页面。

Interior Design 的界面是：

- 左侧固定工具导航。
- 中间输入面板。
- 右侧大预览区。
- 预览区上方切换 Preview / History。
- 结果下方有 Regenerate、Download、Open in editor。

它用 `Template / Custom` 控制输入复杂度：

- Template：选择住宅/商业、房间类型、风格、灯光。
- Custom：这些结构化选项收起，主要通过文字描述。
- 输入框附近还有 Keep layout、More greenery、Oak floors 等快捷短句。

我实际点击 Custom 后，看到了这种参数收起行为。[工作区截图](/Users/mohanlu/.codex/visualizations/2026/10/02/01a0fdb0-2827-7352-b52a-44d15e02f65b/coohom-workspace.jpg)

结果区使用前后对比滑块，让用户直接判断哪里发生了变化。[Interior Design 官方页面](https://www.coohom.com/interior-design-ai)

**你可以学它的快捷表达，但不用把表单和聊天分成两种必须选择的模式。**

例如 Eva 旁边可以出现：

> 保留现有家具　增加收纳　只改这个角落

用户点一个，等同于输入一条明确需求，仍然留在同一个对话与项目里。

你的方案比较还应比前后滑块更进一步：两个方案使用相同视角，切换时突出家具移动、尺寸、价格和动线变化。否则用户只能比较“哪张更漂亮”，无法判断哪个更适合生活。

**Coohom 的边界说明也很有参考价值。**

它明确说 AI 生成图是概念，报价前需要在编辑器里替换成有真实 SKU 和尺寸的目录模型；我点击 Open in editor 后进入了登录弹窗，未验证后续转换是否完整。[概念图与实际产品的说明](https://www.coohom.com/interior-design-ai)

还有一个命名问题：`Furniture & Materials` 页面实际上说明该工具只处理表面颜色，换家具要去 Interior Design。这种“功能名称看似包含、进入后却不支持”的情况，你应该避免。[该工具的范围说明](https://www.coohom.com/furniture-change-ai)

同样，页面上出现“3D”“Walkthrough”字样，也不能直接当成你需要的自由第一人称走动和真实动线检查。

**6．obeeba：商业逻辑与你接近，但目前只能借鉴方向，不能据此决定按钮和操作细节。**

它公开表达的流程非常清楚：

> 扫描房间 → 编辑或让 AI 设计 → 购买场景中的实际家具。

官方描述包括手机扫描、调整墙体与地面、移动家具、按风格和预算生成、使用合作厂商的真实 SKU。网站同时标明产品处于 iOS TestFlight Beta 阶段。[应用说明](https://www.obeeba.com/app)

**最值得学的是“设计建议从可买的东西出发”。**

这与你的模块化产品尤其相关：Eva 推荐的柜子，最好一开始就是能由你的板件和连接规则组成的柜子，随后才谈配色、摆放和购买。

但你的场景比它宣传中的“画面里都可以买”更复杂。你还要容纳：

- 用户已有的沙发。
- 仅作比例参考的传统家具。
- 尚未对应商品的灵感对象。
- 能购买的模块化家具。

这些应该共存在房间里，但购买清单只收用户明确决定购买的可售配置。

目前公开图片与网页无法让我验证它的多选、对象高亮、撤销、版本保存、购物车和扫描精度。所以我不会建议你“照搬 obeeba 的某个浮动菜单”，因为证据不够。

**把这些参考真正用到 Furnishes，应该形成怎样的操作？**

我的建议是：**保留开放房间画布，同时让项目位置、操作入口和当前目标始终稳定。** 正式感来自行为的一致性、状态的明确和结果的可恢复；浮动控件本身并不会让产品不正式。

可以用下面六个实际过程检验设计。

**① 用户已经在房间里，想增加收纳。**

点“添加家具”，或直接说“门口太乱了” → Eva 根据当前房间提出少量必要问题 → 显示两三个相关方案 → 点一个在房间里试放。

这里学 DecorMatters 的相关目录筛选、RoomAI 的视觉选择。Quiz 是帮助当前决定的小交互，不必把用户送去另一张长表单。

**② 用户点一件柜子，说“这里改成绿色”。**

柜子高亮 → Eva 显示当前目标 → 点“选择板件”后，板件分别可选 → 用户点某片 → 材质选项和 AI 修改都作用于该片。

多选沿用同一套逻辑：明确显示“已选 3 件”，每件可移除。输入区不因为多选再换成另一种功能页面。

这学 Planner 5D 的情境操作，但你的目标必须是实际模型对象。

**③ 用户从商品详情页进入，想看现成家具的效果。**

商品详情 → 点“放到我的房间” → 已有当前项目就直接试放；存在多个项目时只问放到哪个 → 保持刚才的商品颜色与配置 → 在房间里调整位置。

点试放家具，再展开“组成与拼装”，看到同一份板件数量、组成和步骤。关闭后仍回到原位置。

**同一份信息从两个入口访问，属于连续服务；要求用户重新配置、重新选择，才会造成重复感。**

**④ 用户同时喜欢两个方向。**

当前方案 → 点“保留这个想法” → 命名“开放收纳” → 继续尝试“带柜门版本”。

比较时显示两个想法，切换相同视角。查看旧想法是预览；从旧想法继续编辑时创建新的工作副本，保留当前较新的内容。

Moodroom 的 Moods 可以参考，但你的“一份最新自动同步 + 最多 10 个手动想法”要直接体现在状态中，不能让用户把自动保存误解成覆盖所有版本。

**⑤ 用户想知道摆放是否影响走动。**

点“查看” → 选择俯视、整体 3D、走进房间；“显示动线”作为叠加信息开启或关闭。

这些都基于同一份布局。视角改变不应生成另一个独立方案，动线也不应只是 AI 随意画出来的装饰箭头。

这部分在本次六个参考里，没有得到足够证据证明存在与你需求完全一致的实现，需要按你的房间模型逻辑设计。

**⑥ 用户只确定其中一件，准备购买。**

选中家具 → 查看当前配置、尺寸、组成和价格 → 加入购买清单 → 核对后下单。

其他家具继续探索。参考家具、已有家具和未购买的想法不自动进入订单；下单时保留所购买配置的记录，后续修改房间也不应悄悄改变订单。

你最应吸收的组合是：**Planner 5D 让用户明确“正在改什么”，DecorMatters 让用户顺手“找到并试放什么”，Moodroom 让用户知道“这个想法属于哪里、决定到哪一步”。** 而 Furnishes 必须补上的，是这三者与实际模块、尺寸、版本同步和购买配置之间的连续关系。
